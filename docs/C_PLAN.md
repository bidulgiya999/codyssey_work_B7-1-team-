# C 담당 개발 계획

기준: 로컬에 제공된 `경제 숏폼 트렌드 챗봇 팀 개발 계획.pdf` 1~8쪽과 과제 요구사항.
작성일: 2026-10-05. `feature/chat`에 C 담당 코드와 테스트를 구현했다. GitHub 팀 저장소의 A 작업은 별도 `feature/auth` 브랜치에 있고, 아직 C 브랜치에는 통합되지 않았다. 이 문서는 구현 계획과 남은 통합 계약을 함께 기록한다.

사용자 확인: 팀원 모두 이제 시작하며 A·B의 골격/구현은 순차적으로 만들어질 예정이다. 비용을 최대한 줄여야 한다. 사용자가 제공한 `Codyssey API 키 문서.pdf` 1~3쪽에는 잔여 1,000,000토큰(화면 확인 시점), OpenAI 호환 호출 주소, 지원 모델과 차감 배수가 나온다. 실제 비밀 키는 이 문서나 저장소에 적지 않는다.

## 1. 프로젝트와 내 역할

경제·AI 숏폼 제작자가 로그인한 뒤 최근/과거 트렌드를 근거로 오늘 올릴 주제와 후속편을 추천받는 FastAPI 챗봇이다. 최신 정보는 LLM의 기억에 의존하지 않고 B가 수집한 네이버 데이터를 사용한다.

| 담당 | 책임 | C와 만나는 지점 |
| --- | --- | --- |
| A | 앱 초기화, 설정, DB 연결, User, 세션 인증 | 로그인 사용자, DB 세션, 공통 설정을 제공 |
| B | 네이버 뉴스·데이터랩, Q1·Q4 | 트렌드 함수와 시나리오 프롬프트를 제공 |
| **C** | **채팅 처리, Chat, LLM 호출, Q5·Q6** | **요청부터 답변 저장·반환까지 연결** |
| D | 화면, 내 기록 조회, DB 확인 SQL, 배포·통합 문서 | 채팅 API를 호출하고 C가 저장한 기록을 조회 |

C의 소유 파일은 PDF 3·5쪽에 따라 아래 다섯 개다. C 기능 검증용 테스트도 함께 작성한다.

```text
app/models/chat.py
app/routers/chat.py
app/services/llm.py
app/services/scenarios/q5.py
app/services/scenarios/q6.py
tests/test_chat.py          # 제안: API·저장·문맥 검증
tests/test_llm.py           # 제안: 성공·실패·타임아웃 변환 검증
tests/test_scenarios.py     # 제안: Q5·Q6 요구사항·데이터 전달 검증
```

로그인, User, DB 연결, 네이버 수집, Q1·Q4 구현, UI, 로그 조회 API, 배포는 C가 만들지 않는다. 관리자 화면, 별도 프론트 프레임워크, Docker, CI/CD, 캐시, 스케줄러, 채널 프로필, LLM 의도 분류도 추가하지 않는다.

## 2. 가장 먼저 맞출 연동 계약

PDF에 정해진 내용과 아직 없는 내용을 구분한다. 기존 `MISSION.md`의 미정 목록 중 주제·역할·UI·DB·배포 방향은 PDF에서 구체화되었지만, 실제 코드의 인터페이스는 아직 없다.

| 대상 | PDF에 명시된 계약 | 구현 전 확인할 내용 |
| --- | --- | --- |
| A 인증 | 세션 쿠키, `require_login` 의존성 | import 경로, 반환값이 User인지 ID인지, 비로그인 응답 |
| A DB | SQLite, 공통 Base, users/chats | Base·DB 세션 경로, 동기/비동기 방식, 테이블 생성 시 Chat 등록 방법 |
| A 설정 | 환경 변수로 비밀값 관리 | LLM 키·모델·타임아웃 설정 이름과 접근 방식 |
| B 트렌드 | `get_hot_issues(limit=10)` → title/link/pub_date 목록 | 동기 함수 여부, 수집 실패 표현 |
| B 비교 | `compare_periods(keyword)` → recent/past/trend | recent/past의 정확한 구조, 기간, 키워드 허용 범위 |
| B 시나리오 | `async build_prompt(message: str) -> str` | q1/q4 모듈 제공 시점, 실패 처리 |
| C LLM | `async ask_llm(system, messages) -> str`, `AITimeoutError` | 제공자·모델, 제한 시간, 일반 오류 예외 |
| D 화면 | `POST /api/chat` 요청·응답 | 오류 형식, q6에서 이전 주제를 보내는 방식 |

`compare_periods()`에 질문 문장 전체를 검색어처럼 넘기지 않는다. 현재 요청에는 keyword 필드가 없으므로 Q5·Q6 초안은 hot issues와 대화 문맥으로 구성하고, 키워드 추이 비교가 꼭 필요하면 B와 입력 규칙부터 합의한다. 별도 키워드 추출 LLM 호출은 추가하지 않는다.

Q6의 이전 주제는 현재 질문 또는 최근 대화에서 가져온다. `build_prompt(message)`의 인자를 임의로 늘리지 않고, 라우터가 LLM에 전달하는 messages에 대화 문맥을 담는다. 이전 주제가 둘 다 없으면 주제를 물어보게 한다.

## 3. 권장 구현 순서

### 0단계 — 팀 골격을 기다리는 동안 독립 작업

입력 규칙과 최근 5쌍의 메시지 배열 구성 규칙을 작은 함수로 준비하고, Q5·Q6 프롬프트의 출력 형식을 먼저 만든다. 예시는 고정 트렌드 데이터로 테스트한다. 임시 인증·DB·User를 운영 경로에 만들지 않는다. B의 import 경로/모듈이 없으면 프롬프트 문자열을 만드는 독립 함수까지만 준비하고 실제 build_prompt 연동은 이후에 완료한다.

코디세이 제공 안내는 확인됐다. `gpt-5-mini`로 LLM 클라이언트를 먼저 진행할 수 있다. A의 골격이 들어오면 아래 1~7단계의 통합을 순서대로 진행한다. 독립 준비는 통합 완료와 구분한다.

### 1단계 — 공통 골격과 계약 확인

A의 골격이 develop에 올라오면 실제 인증·DB·설정 코드를 읽고 C가 쓸 import를 정한다. 없는 인터페이스를 추측해 운영 코드로 만들지 않는다. LLM은 코디세이의 OpenAI 호환 채팅 주소와 `gpt-5-mini`를 기본으로 한다. 팀의 기존 라이브러리와 동기/비동기 방식을 그대로 따른다.

완료 기준: 로그인 사용자 ID, DB 세션, LLM 설정을 어떻게 받는지 설명할 수 있다.

### 2단계 — Chat 모델과 입력 검증

PDF 3쪽의 필드를 그대로 구현한다: `id`, `user_id`(users.id FK), `mode`, `question`, `answer`(실패 시 NULL), `status`(success/timeout/error), `created_at`.

`mode`는 q1/q4/q5/q6/free 중 하나로 검증하고, 질문은 앞뒤 공백을 제거한 뒤 1~500자로 검증한다. 누락·잘못된 타입·지원하지 않는 mode도 처리한다. 사용자 ID는 요청 본문에서 받지 않고 인증 결과만 사용한다. 생성 시각의 저장 기준과 조회 표시 방식은 A·D와 맞춘다.

완료 기준: 잘못된 입력과 비로그인 요청은 LLM 호출·대화 저장으로 넘어가지 않는다.

### 3단계 — LLM 호출과 최소 채팅 흐름

LLM 클라이언트 하나, 서버 측 키, 명시적 타임아웃만 둔다. 스트리밍·여러 제공자 자동 전환·자동 재시도는 넣지 않는다. 처음에는 테스트 대체 응답으로 `요청 → LLM → DB 저장 → 응답` 한 경로를 확인한다.

라우터에는 이해하기 쉬운 순서대로 코드를 두고, 문맥 조회·저장 등 반복되는 부분만 같은 파일의 작은 함수로 분리한다. 별도 repository/service 계층이나 범용 플러그인 구조는 만들지 않는다. 네트워크를 기다리는 동안 불필요한 DB 쓰기 잠금을 유지하지 않는다.

완료 기준: 성공 응답은 DB 저장 성공 후에만 반환하고, 반환한 chat_id가 실제 행과 일치한다.

### 4단계 — 최근 5개 Q/A와 사용자 분리

인증된 사용자의 성공한 대화 중 answer가 있는 최근 5행을 조회한다. `created_at`, `id` 등으로 정렬 순서를 일정하게 유지하고, 최신 5행을 뽑은 뒤 오래된 순서로 user/assistant 메시지 10개를 구성한다. 현재 질문은 맨 마지막에 한 번만 넣는다.

사용자 기준으로 문맥을 유지하며 모드가 바뀌어도 연결한다. 실패 행과 다른 사용자 기록은 포함하지 않는다. 5개의 메시지가 아니라 **5쌍의 질문·답변**이다.

완료 기준: 6쌍 이상일 때 오래된 기록이 제외되고, 다른 사용자의 기록이 섞이지 않는다.

### 5단계 — Q5·Q6 및 mode 연결

- Q5: 반전·비교·논쟁·정보·경험의 다섯 각도를 사용해 총 5~10개 주제와 최종 추천 1개를 요청한다. 추천 이유를 제공된 근거와 연결한다.
- Q6: 이전 주제에서 이어지는 1→2→3편 구성과 오늘 올릴 편 1개, 연결 이유를 요청한다. 이전 주제가 없으면 확인 질문을 하게 한다.
- q1/q4는 B의 `build_prompt()`를 호출한다. C가 내용이나 수집 기능을 복제하지 않는다.
- free는 상세 시나리오가 없어 최신 자료를 지어내지 않는 기본 경제 숏폼 대화로 최소 구현했다. 팀의 최종 제품 의미는 통합 시 확인한다.
- 외부 자료는 참고 데이터로 표시한다. 자료가 없으면 최신 추세를 확인하지 못했다고 안내하며 숫자·추세·출처를 지어내지 않게 한다. 시장 전체를 완전히 조사했다는 표현도 피한다.

완료 기준: 테스트용 트렌드가 실제 system 프롬프트에 전달되고, 최근 대화는 별도 messages로 함께 전달된다. 실모델 출력의 개수·형식은 수동 시연으로도 확인한다.

### 6단계 — 실패 처리와 이벤트 로그

PDF 확정 응답:

```json
{"chat_id": 987, "answer": "추천 내용"}
```

```json
{"error": "AI_TIMEOUT", "message": "현재 응답이 지연되고 있어요. 잠시 후 다시 시도해 주세요."}
```

성공은 200, AI 타임아웃은 504, 입력 오류는 422/INVALID_INPUT이다. FastAPI 기본 입력 오류 형식과 PDF의 최상위 error/message 형식이 다를 수 있으므로, A의 공통 오류 처리와 맞추거나 C 라우트에 한정해 처리한다. 다른 라우트의 오류 정책은 덮어쓰지 않는다.

PDF에 없는 일반 AI 오류의 HTTP 상태는 `502 / AI_ERROR`, DB 오류는 `500 / DB_ERROR`를 제안한다. 이는 팀 합의 전 초안이다. 예외 상세나 API 키를 응답으로 반환하지 않는다.

AI 실패는 가능하면 `answer=NULL`, `status=timeout 또는 error`로 저장한다. DB 저장 자체가 실패하면 rollback하고 `db_save_fail`을 기록한다. 저장하지 못했는데 저장됐다고 응답하지 않는다. AI 실패 기록 저장까지 실패하면 DB 오류를 반환하고 원래 AI 실패도 로그에 남기는 방식을 제안한다.

기록할 이벤트는 `request_received`, `ai_call_start`, `ai_call_success` 또는 `ai_call_fail`, `db_save_success` 또는 `db_save_fail`이다. 사용자 ID·mode·chat_id·오류 종류 정도만 남기며 API 키·세션 쿠키·전체 대화는 로그로 출력하지 않는다.

완료 기준: 타임아웃과 저장 실패 이후의 다음 정상 요청도 처리된다.

### 7단계 — 실제 연동 및 PR

A·B가 제공한 실제 구현으로 C 테스트를 다시 실행하고 D가 사용하는 요청·응답을 확인한다. LLM 실호출은 별도 수동 확인으로 한 번 수행하며, 자동 테스트는 외부 과금이나 네트워크에 의존하지 않는다. PR은 로컬 대체물 없이도 A·B의 합쳐진 코드에서 실행되어야 한다.

## 4. 다른 담당자 없이 개발하는 최소 방법

운영 코드가 로컬 대체물을 import하지 않게 한다. A·B가 준비됐으면 이 구성 자체를 만들지 않는다.

```text
app/                    C 소유 파일만 구현. A·B의 실제 계약 사용
tests/                  C의 회귀 테스트. 테스트 내부의 작은 대체 함수 허용
.local-c/               필요할 때만 만드는 개인 실행 도구. PR 제외
  run.py                로컬 FastAPI 실행·라우터 등록·대체 함수 연결
  fakes.py              고정 사용자·트렌드·LLM 응답 등 꼭 필요한 값
```

- A 골격이 없으면 우선 A·B 없이 작성 가능한 프롬프트와 순수 함수부터 진행한다. 라우터·DB 통합은 실제 골격을 받는 것을 우선한다.
- 로컬 API 실행이 꼭 필요할 때만 `.local-c/`에 작은 실행기를 둔다. 회원가입 화면이나 인증 서버, 네이버 수집기를 재구현하지 않는다.
- A의 DB Base·인증 import가 아예 없으면 dependency override만으로 해결되지 않는다. 가짜 A 운영 파일을 app에 만들거나 sys.modules 조작으로 숨기지 말고 해당 통합을 보류한다. 실행 가능한 척하지 않는다.
- 실제 의존성이 존재하면 로컬 실행기에서 FastAPI 의존성을 override하고, B·LLM 호출은 실행기/테스트에서만 교체한다. 운영 코드에 MOCK_MODE, fallback 로그인, 임시 사용자 ID를 넣지 않는다.
- 임시 데이터는 고정 샘플이라고 명시한다. 로컬용 DB에는 실제 계정이나 비밀값을 쓰지 않는다.
- `.local-c/`를 만들 때 `git rev-parse --git-path info/exclude`로 찾은 개인 제외 파일에 `/.local-c/`를 추가한다. 공용 .gitignore는 이를 위해 수정하지 않는다. 이미 추적된 파일에는 ignore가 적용되지 않으므로 상태를 확인한다.
- PR에서 빼는 것은 타 담당자의 **로컬 실행 대체물**이다. C의 동작을 검증하는 테스트와 테스트 전용 작은 fake는 PR에 남긴다.
- A의 라우터 등록·Chat 테이블 등록·공통 의존성 추가는 별도 연동 요청으로 전달한다. 필요 변경은 숨기지 말고 PR 의존성에 적는다. C 테스트는 가능한 한 A의 User·Base와 임시 SQLite를 사용한다.

## 6. PR과 평가 설명

PDF 7쪽 기준: feature/chat → develop, 최종 develop → main. PR마다 1명 이상 승인, merge commit 방식. C 작업을 다음 세 묶음으로 제안한다.

1. Chat 모델·입력 검증·기본 파이프라인·LLM 클라이언트.
2. 최근 5개 문맥·사용자 분리·모드 연결·Q5·Q6.
3. 오류 처리·로그·통합 검증·설명 보완.

각 묶음 안에서 기능이나 검증이 실제로 완성될 때 의미 있는 커밋을 남긴다. PDF의 C 체크 항목 10개를 기준으로 이력을 관리하되, 빈 커밋·기계적인 파일 쪼개기로 수를 채우지 않는다. 이 저장소에는 `main` 초기 문서 커밋과 `develop`·`feature/chat` 브랜치를 만들었고, 원격은 아직 없다.

PR 직전에는 기준 브랜치와 비교해 파일 목록을 확인한다. 위의 C 소유 코드·테스트·필요한 C 문서만 포함하고 `.local-c/`, .env, DB 파일, A/B/D 임시 구현이 없는지 확인한다. 문서와 진행 로그의 팀 저장소 포함 여부는 팀 규칙을 따른다. 기능 검증에 필요한 테스트를 삭제해 범위를 줄이지 않는다.

평가자에게는 다음 흐름으로 설명한다.

> 저는 채팅 처리 파이프라인과 Q5·Q6를 담당했습니다. 로그인 사용자의 질문을 검증하고, 그 사용자의 최근 성공 대화 5개와 트렌드 자료를 AI에 전달합니다. 답변은 사용자 ID와 함께 저장한 뒤 반환합니다. AI가 늦거나 실패하면 오류를 안내하고 실패 이력도 남깁니다. 인증·데이터 수집·화면은 팀원이 맡은 모듈과 정해진 함수/API로 연결했습니다.

시연 순서: Q5의 5~10개 주제·추천 1개 → Q6 후속 3편과 오늘 올릴 편 → 이전 대화 연결 → D의 내 기록 조회 → 빈 입력·타임아웃 안내. 계정 두 개의 문맥 분리와 DB 실패는 테스트 결과로 보충한다. 실제로 확인한 결과만 완료로 보고한다.

## 8. 비용을 최소화하는 LLM 선택

2026-10-05 사용자 제공 PDF 및 대안의 공식 자료 확인 기준. **코디세이 API를 기본으로 사용**한다. 실제 연결이 막히거나 한도가 소진될 때만 무료 API 하나를 다시 검토한다. 여러 제공자를 동시에 구현하거나 자동 전환하지 않는다. 연동은 `llm.py` 한 파일에 모으고 `ask_llm` 계약을 유지한다.

| 후보 | 판단 | 확인할 사항 |
| --- | --- | --- |
| 코디세이 잔여 100만 토큰 | 기본 선택. PDF에 서버 호출 주소와 `gpt-5-mini` 예제·0.5배 차감이 있음 | 실제 키로 1회 호출, 월 갱신/유효기간, 입출력·추론 토큰 차감 기준, 배포 서버 호출 가능 여부 |
| Gemini API 무료 등급 | 코디세이 API를 못 쓰는 경우 첫 대안 | 계정에서 무료로 제공되는 모델과 한도 확인. Q5·Q6 한국어 결과를 소수 샘플로 평가 |
| Groq 무료 등급 | 다른 무료 대안 | 모델별 분/일 요청·토큰 제한 확인. 한국어 결과와 최근 5쌍 길이에 대한 적합성 검증 |

제공 PDF 1~3쪽에 `https://copa.codyssey.kr/v1/chat/completions`와 `Authorization: Bearer <virtual-key>`가 명시돼 있다. `gpt-5-mini`는 이 주소의 예제 모델이며 차감 배수가 0.5다. 따라서 서버에서 호출할 수 있는 API 형식은 확인됐다. 화면의 활성 키 1개와 잔여 100만 토큰은 **PDF 캡처 시점의 상태**다. 실호출 성공이나 현재 잔여량까지 입증하지는 않는다.

C는 A의 `app.config.settings`가 `.env`에서 읽는 `LLM_API_KEY`, `LLM_MODEL`, `LLM_TIMEOUT_SECONDS`를 그대로 사용한다. URL은 코디세이 제공 PDF의 `/v1/chat/completions` 주소로 고정해 불필요한 설정을 늘리지 않는다. 모델이 비어 있으면 `gpt-5-mini`, 타임아웃은 A의 기본값 30초다. 실제 키만 로컬 `.env`/배포 환경에 둔다. 기존 `ask_llm(system, messages)` 인터페이스를 유지하고 실제 응답 형식은 첫 실호출로 확인한다.

### 현재 통합 계약

`app.models.chat.Chat`은 `app.database.Base`가 SQLAlchemy 2.x Declarative Base이기를 기대한다. A의 `users` 테이블에 `id` PK가 있어야 한다. A가 앱을 만들 때 Chat 모델을 import해 테이블을 등록하고 아래처럼 C 라우터를 등록하면 된다. 아래는 호출 모양을 설명하는 예시이며 A 파일을 C가 만들지는 않는다.

```python
from app.routers.chat import create_router
app.include_router(create_router(require_login, get_db))
```

`require_login`은 인증된 사용자 객체(`.id` 정수)를 반환하고 `get_db`는 동기 SQLAlchemy `Session`을 제공해야 한다. A의 실제 계약이 다르면 C 라우터의 이 한 지점만 수정한다. `httpx`도 공통 의존성에 추가해야 한다. B는 PDF 계약의 `app.services.trend.get_hot_issues(limit=5)`와 `app.services.scenarios.q1/q4.build_prompt(message)`를 제공해야 한다. Q5·Q6는 자료가 없을 때 B가 빈 목록을 반환한다는 계약에 기대고 있다.

현재 로컬 검증은 테스트 전용 A 계약과 고정 LLM 응답을 사용한 26개 테스트 통과다. 실제 A 인증·DB, B 트렌드/Q1·Q4, 코디세이 실호출, D 화면·로그 조회, 배포는 미검증이다. 이 확인이 끝나기 전에는 PR이 완전한 통합 기능이라고 설명하지 않는다.

Gemini 무료 등급은 일부 모델에 무료 입력·출력 토큰을 제공하며 제한이 있다. 무료 등급 데이터가 제품 개선에 사용될 수 있다는 정책도 팀이 선택 시 알아야 한다. Groq도 무료 등급이 있지만 조직/모델별 제한이 있고 초과 시 429가 반환된다. 정확한 한도는 실제 계정에서 확인한다.

출처: 사용자 제공 `/Users/jihwanjeong/Downloads/Codyssey API 키 문서.pdf` 1~3쪽, [Gemini 공식 요금](https://ai.google.dev/gemini-api/docs/pricing), [Gemini 사용량 제한](https://ai.google.dev/gemini-api/docs/rate-limits), [Groq 사용량 제한](https://console.groq.com/docs/rate-limits).

`gpt-5-mini` 0.5배가 요청의 모든 사용 토큰에 동일하게 적용된다는 **가정**이라면, 요청당 원시 사용량 5,000토큰은 잔여량에서 약 2,500토큰을 차감해 약 400회, 10,000토큰은 약 5,000토큰을 차감해 약 200회다. 실제 차감에는 현재 질문뿐 아니라 시스템 프롬프트·트렌드 자료·재전송하는 최근 5쌍·출력, 제공자가 계산하는 추론 토큰 등이 영향을 줄 수 있다. PDF에 차감 계산식 전체가 없으므로 보장 횟수가 아니다. 시연 전에 작은 실호출 1회와 콘솔 잔액 전후 비교로 확인한다.

최소 비용 운용 규칙:

1. 자동 테스트는 가짜 LLM 응답만 사용한다. 실호출은 시나리오 확인·통합·시연에 한정한다.
2. 사용자 요청당 LLM 호출 1회. 분류·키워드 추출·요약을 위한 추가 AI 호출은 넣지 않는다.
3. 최근 5쌍만 전달하고 트렌드는 필요한 소수 기사/지표로 한정한다. 기사 본문 전체나 불필요한 데이터는 넣지 않는다.
4. 답변은 짧은 목록 형식으로 지시하고 제공자별 출력 상한을 설정한다. Q5의 개수·Q6의 3편 구성을 충족하는지는 실호출로 확인한다.
5. 제공자 SDK의 기본 자동 재시도도 확인해 숨은 추가 호출을 막는다. 429/할당량 소진 시 안내하고 유료 모델로 자동 전환하지 않는다.
6. 제공자가 반환하는 토큰 사용량이 있으면 기존 로그에 수치만 남긴다. 별도 사용량 테이블·관리 화면·캐시는 만들지 않는다.
7. 한도 소진 시 실패 처리한다. 비용 최소화 요청을 근거로 유료 플랜 등록이나 자동 결제 설정을 진행하지 않는다.
