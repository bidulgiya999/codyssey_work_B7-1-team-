# C 구현 에이전트 인수인계

다른 에이전트에게 이 파일을 읽고 작업하도록 요청하면 된다. 계획은 [C_PLAN.md](C_PLAN.md)에 정리했다. 근거 PDF와 과제 요구사항은 사용자 로컬 자료에 있으며 이 PR의 변경 파일에는 포함하지 않는다.

## 작업 목표

경제 숏폼 트렌드 챗봇의 **C 담당 기능만** 완성·통합한다. C의 Q5·Q6, LLM 클라이언트, Chat 모델, 채팅 라우터, 테스트는 이미 `feature/chat`에 구현됐다. A·B가 준비되면 C_PLAN의 현재 통합 계약에 따라 연결하고 실제 동작을 검증한다. 사용자에게 설명하기 쉬운 작은 함수와 명시적인 처리 순서를 유지한다.

사용자 확인 사항: 팀원 모두 이제 시작하므로 A·B가 이미 구현됐다고 가정하지 않는다. 비용 최소화가 우선이다. 사용자가 제공한 `Codyssey API 키 문서.pdf`에는 캡처 시점 잔여 100만 토큰, `https://copa.codyssey.kr/v1/chat/completions`, `gpt-5-mini` 예제와 이 모델의 0.5배 차감이 명시돼 있다. 이 모델을 기본으로 구현한다. 실제 키·응답·차감 방식은 실호출로 확인한다. 키 값은 채팅/저장소에 노출하지 않는다. 불가능하면 Gemini/Groq 무료 등급 중 하나만 재검토한다. C_PLAN 8절 참고. 자동 유료 전환·다중 제공자 프레임워크를 만들지 않는다.

1. 실제 작업 저장소가 `/Users/jihwanjeong/Developer/cds-ai-chatbot`인지 확인한다. ChatGPT 미러의 sources는 읽기 전용이다.
2. 적용되는 AGENTS.md, C_PLAN.md, MISSION.md, 팀 PDF, 현재 코드·Git 상태를 읽는다. 사용자 변경을 덮어쓰지 않는다.

## 구현 지침

1. A의 Base·DB 세션·require_login·설정을 재사용한다. 인증 사용자 ID만 신뢰한다.
2. PDF Chat 스키마를 구현한다. 실패 답변은 NULL, status는 success/timeout/error다.
3. 입력은 공백 정리 후 1~500자, mode는 q1/q4/q5/q6/free를 검증한다. free의 실제 동작은 먼저 확인한다.
4. 라우터 흐름은 `인증 → 검증 → 본인 문맥 조회 → 시나리오 → LLM → 저장 → 반환`이다. 동일 파일의 작은 보조 함수만 우선 사용한다.
5. 문맥은 해당 사용자의 성공한 최근 Q/A 5쌍만 오래된 순서로 전달하고 현재 질문을 한 번 추가한다.
6. `async ask_llm(system: str, messages: list[dict]) -> str`을 제공하고 타임아웃은 AITimeoutError로 변환한다. 제공자 SDK/공식 문서를 실제 구현 시 확인한다. 임의의 최신 모델명·API를 추정하지 않는다.
7. q1/q4는 B 함수를 그대로 호출한다. q5/q6는 `async build_prompt(message: str) -> str` 계약을 지킨다. 문맥은 라우터의 messages로 전달한다.
8. Q5는 다섯 각도로 5~10개와 추천 1개, Q6는 1→2→3편과 오늘 올릴 편을 요청한다. 트렌드가 없으면 근거 부족을 밝히고 추세·숫자를 만들어내지 않는다. 이전 주제가 없으면 물어보게 한다.
9. AI 실패·타임아웃 행도 가능하면 저장한다. DB 실패는 rollback하고 별도 오류로 처리한다. 저장 실패를 성공으로 반환하지 않는다.
10. request_received, ai_call_start, ai_call_success/fail, db_save_success/fail 이벤트를 남긴다. 비밀값이나 전체 대화를 로그로 남기지 않는다.

## 대체물과 PR 분리

- A·B가 준비됐으면 별도 대체 실행기를 만들지 않는다.
- 필요한 경우에만 `.local-c/`의 실행기·고정값으로 로컬 실행을 보조하고 개인 Git 제외 설정에 넣는다.
- 운영 코드에서 `.local-c/`를 import하거나 개발용 로그인 우회·MOCK_MODE 분기를 넣지 않는다.
- A 모듈 자체가 없으면 먼저 독립 함수/프롬프트 작업을 하고 DB·라우터 통합을 미룬다. 운영 경로에 가짜 A 파일을 만들지 않는다.
- 테스트 내부의 작은 fake는 테스트와 함께 PR에 남길 수 있다. 사용자 요청은 타 담당자의 부가 구현을 빼라는 의미이며 C 회귀 테스트를 없애라는 의미가 아니다.
- 로컬 대체물을 제외한 실제 통합 환경에서도 검증한다. A·B가 없어서 못 한 검증은 명시한다.
- 사용자 요청 없이 커밋 수를 채우거나 PR을 실제 발행하지 않는다. 구현 요청의 범위에 따라 작업하고 PR 준비 시 파일 목록·검증 결과·연동 의존성을 정리한다.

## 진행 순서와 완료 조건

C_PLAN의 0단계 독립 준비와 C 구현은 끝났다. 현재 26개 자동 테스트는 외부 LLM을 호출하지 않고 통과한다. A·B가 들어오면 실제 연동 테스트, 첫 코디세이 실호출, D 화면과의 계약 확인을 진행한다. LLM 실호출 성공 여부와 자동 테스트 성공 여부를 구분한다. 새 프레임워크나 다중 계층 구조를 추가하지 않는다.

완료 보고에는 변경 파일, 동작 흐름, 실행·검증 방법, 통과/미실행 항목, 타 담당자에게 필요한 연결 작업을 적는다. 기능 단위 완료와 결정은 저장소 `docs/PROGRESS.md`에 기록한다. `~/Developer/lifebase`는 수정하지 않는다.
